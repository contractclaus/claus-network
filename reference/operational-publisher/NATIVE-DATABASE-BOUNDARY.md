# Native database and configuration boundary

R24 removes the table-owner database credential from Native. A dedicated `claus_native_runtime` role retains the existing work-table reads/writes, but cannot create/alter/drop persistent tables, truncate them, assume the owner role, write `claus_config`, or access the retired Native Jobs-wallet tables. The actual wallet remains in its existing fixed custodian.

Native's existing initializer paths verify the current schema in managed mode instead of running DDL. The deployment checks all 519 expected columns in the existing 70 tables. Additional columns are allowed; missing or changed required columns fail explicitly. Fresh database provisioning remains an operator action. Existing records, sequence values, work IDs, leases and financial holds are not copied or reset.

Configuration changes move to `/api/native-configuration` on the fixed operator service. Its distinct key never enters Native. The database role can read/append configuration and append the corresponding journal entry, but cannot rewrite old configurations, change work records or alter schema. Writes validate the original configuration schema, compare the expected revision, and record configuration and journal together. Retrying the latest completed identical request returns its existing revision; older conflicting revisions remain conflicts. Native's old configuration write route returns 410; private operator tooling uses the fixed route directly.

Activation order: preserve exact source and private credentials in the encrypted checkpoint, install the new narrow DB roles, verify actual denied privileges, install the fixed configuration route, switch Native to the runtime role, observe the original handoff draining, and only then disable the former table-owner login. The old role continues to own tables but cannot log in and has no password. Provider deployments using its former connection string must not be restored as working runtimes.

This is not general host isolation. Native still writes work/review/release/control tables and holds other client credentials. API database isolation is separate. General Node or SQL source editing remains unavailable; only the existing isolated network/work JSON modules are editable. No new payment, paid review, schedule, mainnet action, fee change or operator X post belongs to R24.

Backup continuity uses a third, operator-local read-only role (`claus_native_backup`). Its key is absent from deployments. It can read all original 70 tables and 7 sequences, including retired ledgers that the runtime cannot read, and an actual attempted write is denied. Future private snapshot credential files use `memory.services.agent.backupUrl` rather than the runtime URL. Existing encrypted snapshots and restore evidence remain unchanged; this is an access check, not a new restore or production cutover.
