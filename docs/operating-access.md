# Claus operating access

Claus and the network owner's own projects use available funding and execution capacity, rather than public subsidy counters. The identity check uses the stored Ethereum principal and current project ownership while the existing continuous-operation capability is enabled. Names, slugs and caller-supplied flags cannot select this mode. Pending transfers and archived projects do not qualify.

The operating path removes owner/project daily review counts, the cumulative review admission ceiling, daily approval counts, completed-container-build window counts, project/agent/credential/mandate counts, source and release version counts, compile counts, service version/quote/order counts, worker daily counts and application daily-write counts. Review reservations and approval counts use separate operating records, so operating traffic does not consume public count quotas.

Container builds retain two concurrent slots and one unresolved build per project. Uncertain operations keep their original identity and reservations. Workers keep their real execution and queue capacity. Storage byte ceilings, per-request sizes and sandbox limits still apply.

The native Claus Builder no longer stops at its own project model-request count, daily model/test counts, local model budget or version count. The separate payer remains authoritative for actual money. Other members retain their existing Builder allowances. Web research and private search have no internal daily read-count quota; cached results, original request keys, in-flight leases and provider throttling remain.

This does not create funds or approvals. Other participants’ runtime reviews still need a valid quote, real funded balance, independently produced report and the actual Claus decision. Claus-owned runtime applications may use the explicitly labelled owner-operator report described in sources-and-builds.md. Per-review spending ceilings, payment custody, revocation, contract protections, fee recipients, external provider limits and the prohibition on a second self-issued CLAUS token remain in force. Public projects retain their existing admission policy.

Claus’s operational code lane now includes core API, Native and website application modules, new files, dependencies and build configuration, plus public Network repository source. It retains the exact base revision, source-bound review, immutable deployment identity, private Native archive, live health verification and previous-deployment rollback. Rollback restores code rather than reversing database writes. Isolated QuickJS entry files keep their own contract.

The operator role can diagnose deployment alignment and original failed/pending operations, make routine application changes and allocate existing server funding without an additional founder approval. The protected signing and spending services remain separate. Runtime work continues across ordinary deployment handoff; a code update does not replace the original mission or work records.

Model usage, paid external APIs and maximum authorized server lease commitments share the owner-configured rolling operating budget. This accounting is a commitment ceiling rather than a provider invoice. Unknown reservations remain held; actual provider credit, capacity and account access still determine availability. Pooled project grants and non-expiring service maintenance remove artificial per-project sunsets. Existing fixed hosting subscriptions and separate financial mandates retain their own accounting.

Own website DNS supports A, AAAA, CNAME, TXT, MX, CAA, NS, SRV, HTTPS and SVCB records, including underscore service labels and leftmost wildcards within claus.si. MX priority and structured record data are retained during reconciliation. Proxied records use automatic TTL. The protected website administration service keeps provider credentials out of application source and model output. Development commands use the same published and enforced limits: 10–900 seconds, up to 64 supplied files and four unresolved runs; there is no separate daily run-count quota.

Owned work now supports parent goals, explicit dependencies, durable revision history and separate prepared, deployed, usable and used result stages. These stages record the agent’s assessment and evidence, not an independent audit. The private manage_resources tool creates owned GitHub repositories and Vercel projects, reads deployment diagnostics, creates encrypted application secret references, rotates and revokes them, and binds selected versions to production environments. Worker grants are limited to named resources and original active work; completing or cancelling that work disables broker access. Ordinary application secrets require rebinding and redeployment after rotation or revocation. Credentials are not returned to the model. Infrastructure spending continues through the shared operating budget.

Own Runpod workloads may request a GPU count and minimum VRAM per device. The quote accounts for every requested GPU, and total host CPU/RAM requirements are divided across those devices. The new operating profile supports up to eight GPUs when available within the shared budget; existing profiles, live instances and reservations retain their identities. Owned applications can provision an isolated PostgreSQL schema and login in the dedicated application database, use vector and trigram extensions, bind the encrypted connection reference, apply retained transactional schema migrations, and rotate or revoke the login. Revocation blocks new database connections; existing sessions must be drained by the application. Current application editing also includes TypeScript module files, and the agent instructions reflect its current source permissions.

Managed repositories now support immutable source inspection, revision-aware file updates and branch creation. Owned Vercel applications can stage a pinned repository commit with resumable file uploads, reserve their Basic build maximum against the shared operating budget, inspect deployment logs, and promote after source, readiness and health checks. Repeating the original request ID reconciles a lost response without starting a second build. Earlier tracked deployments can be promoted for code rollback; this does not restore database contents. Secret binding also rejects a version that was rotated while its action was pending. These are operator-installed capabilities; their availability is not evidence that Claus has independently delivered a new product.

Owned resources now include a versioned capability catalog and durable provider or human dependency records linked to existing work. Observed provider identity is distinguished from configured access and agent-recorded evidence. The private large-object storage interface supports resumable multipart uploads, expiring signed URLs and full-object SHA256 verification with an encrypted checkpoint. The dedicated R2 management credential is connected for owned storage. Every prepared upload reserves its retention-period maximum against the shared operating budget. Buckets have explicit retention and incomplete-upload expiration; historical resource records are retained. These capabilities were installed by the operator; no autonomous usage or product delivery is implied.

The dedicated R2 management connection is installed for private owned storage. The service endpoint registry adds versioned HTTPS API and model integrations with bounded JSON input schemas, secret references, expiry and revocation. Each billed call reserves its declared maximum against the existing shared operating budget; these authorizations are distinct from authenticated provider invoices. Provider-side controls are needed where actual usage could exceed that maximum. Responses are retained encrypted and read in explicit pages. Lost responses never trigger an automatic duplicate request. Registered descriptions and price references are operator/agent assertions until supported by actual provider evidence. No extra subscription or model is purchased by registering an endpoint.

Claus can select a second compute provider through its own Fly.io organization. The enrolled postpaid profile uses the existing authorized card; it does not create a provider deposit or share Runpod credit. Each original lease is admitted through the common USD200 rolling24h / USD6000 rolling30d operating budget. CPU, additional RAM and region are priced from the current official Fly pricing page. A per-lease transfer budget is included and monitored; loss of metering or exhausted transfer authorization stops the original machine. Provider metering and shutdown delays can exceed estimates, so these authorizations are not a hard provider invoice cap. Unsettled bills remain visible. Seven regions and isolated per-project applications are available; no machine is created solely to demonstrate access. Runtime request schemas now expose GPU count, VRAM, postpaid grants and egress allowance consistently to Claus.

Research can use the shared operating budget without the legacy three-idea, one-job, 24-step or 30-USDC local quotas. The owner-selected null settings remove only those technical and duplicate model limits. Original effect IDs, pending payment reservations, per-request model ceilings and the separate IMD token mandate remain enforced. Work resumes from retained dossiers, and each ordinary reasoning step can decide to conclude or park an unproductive direction. Real concurrency still depends on the running worker infrastructure. Operator-installed capability is not a claim that Claus independently completed the change.

Owned repositories can use a controlled GitHub Actions build workflow with immutable source and workflow commits, Linux AMD64 or ARM64 runners, up to six hours of runtime, dependency caching and private container publishing. Each build has an original request ID, a shared-budget reservation based on current runner pricing, status, cancellation, logs and private artifact retrieval. Unknown dispatch outcomes are reconciled without repeating the build. Ordinary build artifacts expire after one day and should be copied to owned object storage when needed. Private runtime image pulls additionally require the package-read credential; configuring the build capability does not prove that a paid build or service deployment has run.

Private owned-container releases can now bind a successful original GitHub Actions build to its exact source commit, workflow, artifact and immutable GHCR digest. The image receipt verifies private package ownership and image configuration without downloading gigabyte layers. Private source and owner reports remain private, and the actual Claus owner decision is still required. This path requires a connected package-read credential and an enrolled Runpod private-image profile; while GitHub account verification is pending, it is unavailable. It does not change the independent review path for other owners or the shared operating budget.

Claus can now queue durable endpoint requests under an existing work item. A queue pins the endpoint revision, retains encrypted input, supports dependencies and request concurrency, and preserves original request IDs across interruption. Failed requests and unresolved outcomes remain inspectable; HTTP 202 is recorded as acceptance, not completed external work. The existing infrastructure guardian processes due requests. A signed JSON webhook can enqueue arguments for its fixed endpoint with freshness and replay checks. Provider-specific webhook formats need an adapter. Versioned procedures can be retained from real endpoint or queue receipts, selected for later work and assessed using later evidence; recording a procedure does not prove its use. The dedicated private-package reader and Runpod registry credential are now connected to the private-image profile using the existing prepaid funding account. No paid demonstration build, server or invented queue work was created.

Claus can now grant a new public HTTPS browser origin to an existing work item, retaining the purpose and every revision. The origin becomes unavailable when its work ends, expires or is revoked. Reusable sessions stay tied to their original work and owner. Browser navigation performs a public-DNS check; Browserbase resolves the remote connection. Download actions sync files into the browser provider, and authenticated metadata supplies the original filename, byte count and SHA256. A private five-minute transfer grant streams that exact file through the owner-checked gateway without exposing the provider key or loading the whole file into the model. Consumers verify the full hash before use. No website account, origin grant, download or paid browser demonstration was created for this implementation.

Claus-owned runtime releases can bind versioned application, database and scoped-worker secret references to environment variables on Runpod or Fly.io. Values are resolved inside custody immediately before creation and are never inserted into the release manifest or returned resource observation. Both the release owner and custody approval are checked. The existing guardian stops a resource when a referenced key is revoked, expires, or its worker grant ends. Rotation requires a new manifest binding for future starts; an already running container keeps its old environment until explicitly replaced. Retained old key versions are used to redact runtime logs and provider errors. No application key was bound to an actual server and no paid resource was started by this implementation.

Claus can now store versioned operating definitions for its existing managed applications, secret references, queues and immutable source deployments. Each explicit plan retains actual configuration observations and dependency order. Apply resumes the same original operation and deployment IDs, blocks on intervening changes, respects completed work and disabled definitions, and keeps per-service execution leases. Source, readiness and the existing operating budget remain checked by the original publication path. Definitions do not change protected signer rights or create a new financial mandate. Configuration changes without a deployment target require a later deployment before runtime use. No application was created or deployed merely to demonstrate this capability.

Claus can version its delegated technical runtime settings through the fixed custodian: reasoning effort, response size and actions per continuation chunk. Active work and the current configuration revision are required; an interrupted request recovers its original committed revision. Identity, permissions, models, budgets and global enablement are not editable through this tool. Ethereum and Base wallet, NFT, inference-receipt and compute-funding clients now retain an independent RPC fallback, including when their primary is already a public endpoint. Fallbacks preserve the exact request and original signed transaction bytes; nonce, gas, canonical-receipt and financial-mandate checks still apply. No transaction or runtime configuration change was made merely to demonstrate these capabilities.

Owned application databases now support dimensioned vector columns, HNSW similarity indexes, PostgreSQL full-text search, trigram indexes and expiring key/value cache tables through versioned database migrations. These use the existing isolated application roles and installed extensions. Cache expiry is enforced by application reads and an explicit cleanup job; defining a table does not install background deletion. The original migration IDs, transactional rollback and retained copies before destructive changes remain in place. No dataset, application or customer traffic was manufactured to demonstrate these capabilities.

Private data assets now bind verified owned objects into immutable dataset, checkpoint, model, document and export versions. Their manifests retain original content hashes, provenance, declared usage rights, lineage and object expiration. Versions can be compared, exported and retired without deleting shared files or protected history. Pre-change table copies also preserve the values of generated and identity columns as ordinary stored data. Object lifetime is not extended by a manifest, and a recorded checkpoint or model is not evidence of training or autonomous use.
