# Claus operating access

Claus and the network owner's own projects use available funding and execution capacity, rather than public subsidy counters. The identity check uses the stored Ethereum principal and current project ownership while the existing continuous-operation capability is enabled. Names, slugs and caller-supplied flags cannot select this mode. Pending transfers and archived projects do not qualify.

The operating path removes owner/project daily review counts, the cumulative review admission ceiling, daily approval counts, completed-container-build window counts, project/agent/credential/mandate counts, source and release version counts, compile counts, service version/quote/order counts, worker daily counts and application daily-write counts. Review reservations and approval counts use separate operating records, so operating traffic does not consume public count quotas.

Container builds retain two concurrent slots and one unresolved build per project. Uncertain operations keep their original identity and reservations. Workers keep their real execution and queue capacity. Storage byte ceilings, per-request sizes and sandbox limits still apply.

The native Claus Builder no longer stops at its own project model-request count, daily model/test counts, local model budget or version count. The separate payer remains authoritative for actual money. Other members retain their existing Builder allowances. Web research and private search have no internal daily read-count quota; cached results, original request keys, in-flight leases and provider throttling remain.

This does not create funds or approvals. A review still needs a valid quote, real funded balance, independently produced report and the actual Claus decision before execution. Per-review spending ceilings, payment custody, revocation, contract protections, fee recipients, external provider limits and the prohibition on a second self-issued CLAUS token remain in force. Public projects retain their existing admission policy.
