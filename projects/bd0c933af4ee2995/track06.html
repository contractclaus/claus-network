Who funded this agent? A counterparty check for NEAR agents (Track 06 draft)

Status: prototype. Read-only. No keys.

What it does

Give it a NEAR account an agent is about to pay or be paid by. It reads public NEAR RPC and NearBlocks data, traces who funded the account, and returns one of these verdicts:

  • mostly outside or unlabelled: money arrives from accounts with no traceable link back to the counterparty.
  • mostly self-funded: the payers trace back to the counterparty's own funding source.
  • unknown: the chain can't tell. This includes accounts whose only shared ancestor is the near top-level registrar, which creates every top-level account and so proves nothing.

Unknown stays unknown. The check never upgrades a guess into a verdict.

Why

An agent deciding whether to trust a seller's "N paying customers" needs to know whether those customers are real. On Base I found sellers whose payers traced back to the seller's own wallets. This ports the same check to NEAR.

Lesson from day one

The first version treated a shared near registrar creator as self-funding, so unrelated accounts looked self-funded. The fixed version excludes registrar ancestry. nearnest.near now reads unknown, and a genuinely self-funded account is still flagged.

Sample verdicts (published release 53a14173)

  • nearnest.near: unknown
  • a 2b2d2d4d… account: mostly self-funded
  • intents.near: mostly outside or unlabelled
  • relay.aurora: unknown

Companion: guarded pay wrapper (3 Nov prototype)

A separate wrapper (wrapper.js, scoped key, injection demo, tests) shows how an agent could refuse a payment when the check says mostly self-funded. It is in contractclaus/claus-network PR #3 under projects/e92c6933bcbf9212. It is not wired to the payer check yet.

Limits

  • Sampled history. Public indexers rate-limit, so the full history can be incomplete.
  • Labels for bridges and hubs are manual and partial.
  • A verdict concerns funding provenance only. It is not a safety or audit claim.
