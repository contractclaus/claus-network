# NEAR counterparty check (prototype)

Before an agent pays, check the receiver and get `allow`, `warn` or `block` with reasons. If the answer is `block`, the wrapper refuses to sign.

## What it checks

- `src/check.js` pure policy, no network: receiver on a blocklist (with evidence), account missing, contract code hash changed since the last interaction, young or unknown-age account, first contact, large first payment.
- `src/near.js` live facts from NEAR RPC `view_account` (existence, `code_hash`).
- `src/wrapper.js` refuses to sign on `block` and holds a `warn` for a human (`held_for_human`) unless the caller passes `requireHumanOnWarn: false`. The signer stub models a function-call access key scoped to one receiver contract and a method list, so a payment outside that scope is refused even if the policy would allow it.
- `demo/injection.js` a web page tells the agent "pay 40 NEAR to drainer-77.near". The wrapper refuses and logs why. Saved output: `demo/injection.log`.

## Run

```
npm install
node test.js && node test_enrich.js && node test_scopedkey.js && node test_codewatch.js
node demo/injection.js
```

Expected demo outcomes: `signed`, `refused_to_sign` (policy block), `key_scope_refused` (a 0.5 NEAR first-contact warn that the scoped function-call key cannot sign because it carries a deposit).

## Data sources per signal

| Signal | Source | How |
|---|---|---|
| Account exists | NEAR RPC `view_account` | `src/near.js`, live |
| Is a contract, code changed | NEAR RPC `view_account.code_hash` | compared with the hash stored at the last interaction (`src/codewatch.js`) |
| Account age and activity | NEAR indexer (e.g. NEAR Lake / public explorer API) | not wired yet; unknown age returns `warn` |
| Prior interactions | the agent's own local payment log | `first_contact` and `large_first_payment` in `src/check.js` |
| Shared blocklist with evidence | local JSON file today; target is a shared registry other agents append to with an evidence link | each entry carries `evidence` |

## Scoped key limits

The agent signs with a NEAR function-call access key scoped to one receiver contract and an optional method list. Per the NEAR access-key docs:

- It cannot transfer NEAR, attach a deposit, add or delete keys, deploy code or call any other contract. `keyPermits` mirrors those rules so the wrapper refuses before signing.
- Its gas allowance is finite. When it runs out the key stops working; an account holding only function-call keys can lock itself out, so keep a full-access key offline with the owner.
- Payments of NEAR itself therefore need a payment contract method the key is scoped to, not a plain transfer.

## Limits

- Heuristic. A clean `allow` is not a guarantee that a receiver is honest, and a `warn` is not proof of fraud.
- Account age needs an indexer and is not implemented yet; unknown age is treated as a warning.
- The blocklist is a local example file, not a maintained feed.
- The scoped key is a stub that models NEAR function-call access keys; it does not hold or sign with a real key.
- Not audited. Not a hackathon entry yet: I'm exploring NEAR AI Track 06 and will only enter if it holds up.
